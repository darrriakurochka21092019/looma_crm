# LOOMA.CRM

Версия 1.2.2 CRM для производства мягкой мебели. React 19 + TypeScript, Node.js 24 / Fastify, PostgreSQL 17. Интерфейс на русском языке: светлый фон, белые карточки и фиолетовый акцент.

Клиенты, заказы с несколькими изделиями, производство, документы, задачи и управленческие финансы работают через сервер и PostgreSQL. Данные сохраняются между перезапусками. Доступ к финансовым данным и файлам проверяется сервером.

## Обновление работающей CRM

Для установленной готовой сборки используйте [пошаговую инструкцию обновления](docs/UPDATE_1_1.md). Существующие `.env`, `storage` и PostgreSQL сохраняются; новые миграции применяются автоматически при запуске `start-ready.bat`.

В версии 1.2.1 фото можно загрузить прямо в карточке изделия; оно автоматически подставляется в предложение и приложение.

В версии 1.2.2 убрана зависимость от нативного модуля паролей: Argon2id выполняется через WebAssembly в отдельных потоках. Существующие хеши и параметры защиты сохраняются. При повторном запуске пароль владельца не вычисляется заново; запуск показывает каждый этап для диагностики.

В версии 1.2.0 добавлено создание договора, приложения, предложения и ТОРГ-12 из карточек клиента и заказа: [инструкция](docs/DOCUMENTS.md).

В версии 1.1.0 добавлены архив остановленных заказов с исключением из расчётов, пакетная загрузка документов, полный рабочий доступ менеджера, явное разделение задач по заказам и отдельных задач, уведомления MAX и восстановление после разрыва соединения PostgreSQL. Подключение MAX описано в [отдельной инструкции](docs/MAX.md).

## Быстрый запуск на Windows с Docker

Нужны **Node.js 24 LTS**, **Docker Desktop с Docker Compose** и свободные порты 3001 и 5432. Для Docker на Windows необходимы поддерживаемая версия Windows и включённая виртуализация / WSL 2. Если Docker недоступен, используйте вариант с обычным PostgreSQL ниже.

1. Распакуйте проект в отдельную папку, например `C:\LOOMA\looma-crm`.
2. Запустите Docker Desktop и дождитесь состояния готовности.
3. Дважды нажмите **start.bat**. Первая сборка скачивает зависимости и может занять несколько минут.
4. Откройте **http://localhost:3001**.
5. Логин: **owner@looma.local**. Пароль находится в файле **.env**, строка **SEED_PASSWORD=…**. Пароль генерируется случайно при первом запуске. Откройте `.env` через Блокнот; не передавайте этот файл сотрудникам и не публикуйте его.

`start.bat` создаёт чистую базу с владельцем. Демо-заказы автоматически в рабочую базу не добавляются. Повторный запуск не сбрасывает данные и пароль.

Чтобы добавить демонстрационные данные в ещё пустую базу:

```bash
docker compose exec app node dist/server/seed.js --demo
```

Демо-учётные записи: `manager@looma.local`, `accountant@looma.local`, `master@looma.local`; пароль — текущее значение SEED_PASSWORD на момент их создания. Все имена, телефоны и суммы в демонстрационных заказах вымышлены. Для рабочей базы приглашайте сотрудников через настройки.

Остановка: **stop.bat**. Проверка журналов: `docker compose logs app`. Обновление кода: `docker compose up -d --build`. Команда `docker compose down -v` удаляет базу; не используйте её для обычной остановки.

Если на Linux папка `storage` создана другим пользователем и возникает EACCES, выдайте её владельцу приложения: `sudo chown -R 1000:1000 storage`. В контейнере приложение работает от пользователя node, не от root. На Docker Desktop папка обычно доступна без отдельного изменения прав.

## Запуск без Docker

Нужны Node.js 22.12+ (рекомендуется 24), npm и PostgreSQL 17. Создайте отдельную пустую базу `looma` и пользователя с правами на эту базу через pgAdmin или `psql`. Пример команд администратора:

```sql
CREATE USER looma WITH PASSWORD 'ЗАМЕНИТЕ_СЛУЧАЙНЫМ_ПАРОЛЕМ';
CREATE DATABASE looma OWNER looma;
```

Откройте терминал в папке проекта:

```bash
npm ci
npm run setup
```

В `.env` укажите `DATABASE_URL=postgres://looma:ПАРОЛЬ@127.0.0.1:5432/looma`. Специальные символы пароля в URL должны быть percent-encoded; случайный пароль, созданный setup, уже безопасен для URL. Используйте именно пароль пользователя PostgreSQL, а не пароль входа в CRM.

```bash
npm run db:seed
npm run build
npm start
```

Адрес: **http://localhost:3001**. На Windows дальнейший запуск можно выполнять через **start-local.bat**. Терминал сервера должен оставаться открытым.

Для разработки:

```bash
npm run dev
```

Клиент: http://localhost:5173; API: http://127.0.0.1:3001/api. Vite передаёт запросы `/api` серверу. Миграции автоматически применяются при запуске API. Добавление демо: `npm run db:seed -- --demo`. Команда seed никогда не меняет пароль уже существующего владельца.

## Готовая сборка без Docker

В готовой сборке установка выполняется с `--ignore-scripts`: включённый в пакет готовый модуль Argon2 проверяется напрямую перед запуском. На Windows npm запускается через его JavaScript-файл с помощью Node.js. Это исключает вложенные установочные shell-скрипты и предупреждение DEP0190. Компилятор C++ для этой сборки на Windows x64 не требуется.

Для компьютеров, где установка `esbuild` или других инструментов сборки завершается ошибкой, предусмотрен архив **LOOMA_CRM_READY.zip**. Он содержит собранный интерфейс, сервер и миграции. Node.js и PostgreSQL устанавливаются отдельно; запуск — через **start-ready.bat**. При первом запуске устанавливаются только рабочие зависимости, без Vite, tsx, TypeScript и esbuild.

Готовый архив создаётся командой `npm run package:ready` и прикладывается к успешному GitHub Actions как артефакт **LOOMA-CRM-ready**. При переходе с исходников скопируйте настроенный `.env` рядом со `start-ready.bat`; если уже загружали документы, перенесите также `storage`. Настройки и данные в архив не включаются. Этот способ устраняет необходимость запускать инструмент сборки на целевом компьютере; совместимость конкретной старой версии Windows проверяется при локальном запуске.

## Первые действия

1. Войдите владельцем, откройте профиль внизу меню и задайте свой пароль. Активные сессии будут отозваны, потребуется войти заново.
2. В «Настройки → Компания и расчёты» заполните название, реквизиты и начальный остаток денег. Начальный остаток — реальные деньги до начала ведения учёта в CRM, его нельзя повторно записывать поступлением.
3. Выберите правило и процент налогового резерва. Это оценка для внутреннего планирования; точный налоговый расчёт в MVP не реализован.
4. В «Сотрудники и роли» создайте приглашения. Система показывает ссылку на 48 часов и сама не отправляет письма.
5. Создайте клиента, затем заказ. В одном заказе может быть несколько изделий; цена изделия задаётся за единицу, скидка — на весь заказ.
6. Плановые затраты задаются в изделиях. Фактические расходы добавляйте отдельно в финансовом разделе. Оплату расхода проводите кнопкой «Оплатить» в журнале расходов.
7. Загрузите договор / эскиз в документы заказа. Для автозаполнения нажмите «Создать документы» в заказе и проверьте реквизиты.

Владелец видит всё. Менеджер имеет полный доступ ко всем рабочим разделам: клиенты, заказы, финансы, отчёты, все документы, задачи команды и история заказов. Раздел «Настройки» и его API доступны только владельцу. Бухгалтер ведёт финансы и финансовые документы. Мастер видит свои заказы, техническую спецификацию, технические файлы и назначенные задачи. Приглашённый мастер должен быть назначен на заказ или его этап до назначения задачи с этим заказом.

Менеджер может менять состав, цены и количество изделий на всех стадиях, приостанавливать, отменять и закрывать заказы. Для закрытия требуется подтвердить передачу изделия. Неоплаченный долг сохраняется.

## Правила финансов

Все суммы хранятся в целых копейках; UI показывает рубли. Сервер рассчитывает итоги самостоятельно.

- Приостановленные, отменённые и архивные заказы исключаются из общих финансов, долгов, расходов, денежных движений, графиков, отчётов и рабочих списков задач и документов. История доступна через «Заказы → Архив». При возобновлении суммы и задачи возвращаются в учёт. Неоплаченные резервы пересчитываются по текущим учитываемым заказам; оплаченные остаются историей платежей.
- Цена заказа = сумма цен изделий × их количество − скидка.
- Получено = подтверждённые поступления − подтверждённые возвраты. Черновики в расчёты не входят.
- Долг и переплата отображаются раздельно. Возврат не может превышать сумму полученных денег.
- Фактический расход уменьшает валовую прибыль, даже если ещё не оплачен. Его оплата меняет только движение денег.
- Валовая прибыль заказа = цена − прямые затраты. Пока заказ не закрыт, прибыль предварительная.
- Прибыль периода = валовая прибыль заказов, закрытых в этом периоде, − общие расходы периода. Общие расходы по заказам не распределяются.
- Денежный поток = поступления за вычетом возвратов − оплаты расходов за период.
- Налоговый резерв — настраиваемый процент от положительной базы, с возможностью ручной корректировки и обоснованием. Он не является денежной выплатой.
- Для статуса «Фактически оплачено» сначала создайте общий налоговый расход, оплатите его, затем свяжите оплату с резервом на ту же сумму. Одна оплата не может закрывать несколько резервов.
- «Доступно денег» = начальный остаток + денежные движения до конца выбранного месяца − открытые резервы до этого месяца. Незафиксированный резерв выбранного месяца также включён как оценка.
- Долги и журнал расходов показывают актуальное состояние. Поступления, выплаты и прибыль периода фильтруются по выбранному месяцу. Это подписано в интерфейсе и выгрузке.

Подтверждённые движения не редактируются и не удаляются через API. Ошибки прихода исправляйте возвратом. Расход можно уточнить с записью в аудит, но его новая сумма не может быть меньше уже оплаченной. Полный механизм сторнирования ошибочных исходящих движений — следующий релиз; не создавайте компенсирующий клиентский приход для такой ошибки.

Время компании — Europe/Moscow; даты денежных операций задаются как календарные даты. Время задачи при вводе трактуется как время устройства, что указано в форме.

## Документы и договоры

В карточке заказа доступна кнопка **«Создать документы»**: договор и приложение в DOCX, коммерческое предложение и ТОРГ-12 в XLSX. Данные берутся из клиента, заказа и сохранённых реквизитов компании. Поддерживаются скидки, суммы прописью, фотографии изделий, комплект ZIP и история версий. [Как пользоваться](docs/DOCUMENTS.md) · [Обновление готовой Windows-сборки](docs/UPDATE_1_2.md).

Принимаются PDF, PNG, JPG, DOCX, XLSX, XLS, до 25 МБ на файл. Можно выбрать или перетащить до 10 файлов за одну загрузку, всего до 100 МБ. Вся партия проверяется и сохраняется целиком; при ошибке или нехватке квоты откатывается. Для новой версии отдельного документа выбирается один файл. Проверяются расширение, сигнатура, структура DOCX/XLSX, отсутствие VBA в OOXML, лимит развёрнутого ZIP. Лимиты размера и квоты на документы доступны владельцу. Исполняемые файлы не принимаются. Антивирусный движок в первой версии не подключён.

Файлы хранятся в закрытой папке `storage`, раздаются только после проверки сессии, роли и заказа. Не публикуйте эту папку через nginx / Caddy. Новая версия имеет новый файл; предыдущие версии доступны владельцу и менеджеру. PDF и изображения можно открыть внутри CRM, остальные файлы скачиваются.

`docs/contract-template.docx` — **технический образец с полями**, его условия необходимо заменить. Поля: `{company_name}`, `{legal_details}`, `{client_name}`, `{client_phone}`, `{client_address}`, `{client_details}`, `{order_number}`, `{contract_date}`, `{order_title}`, `{items}`, `{total}`, `{due_date}`, `{payment_terms}`. После загрузки и утверждения шаблона менеджер может сформировать договор из карточки заказа. Обновление шаблона снимает утверждение. Готовый договор сохраняется в документах.

## Импорт Excel и отчёты

Владелец открывает «Настройки → Импорт из Excel», выбирает тип данных, файл и лист, сопоставляет заголовки и нажимает «Проверить строки». В первой строке файла должны быть уникальные заголовки. Поддерживаются .xlsx и старый .xls. Лимит — 10 МБ / 10 000 строк на одну операцию.

Клиенты: обязательны имя и телефон. Заказы: клиент, телефон, цена за единицу, срок; количество по умолчанию 1. Для расходов обязательны категория, сумма и дата. Даты: `ГГГГ-ММ-ДД`, `ДД.ММ.ГГГГ` или настоящая дата Excel. Деньги: `120000`, `120 000,50`, `120000.50`.

Система пропускает ошибки и дубли с пояснениями. Подтверждение выполняется транзакционно. Повтор файла блокируется по содержимому и листу, повтор строки — по нормализованным данным. Существующий телефон не создаёт второго клиента. Импорт заказов может создать расходы ткани / работы / доставки, **без автоматического создания их оплат**. Даты таких затрат берутся из срока заказа; если в исходном реестре есть отдельные даты затрат, импортируйте их отдельным реестром расходов.

Для законно повторяющихся одинаковых расходов используйте ручное добавление: импорт считает полностью одинаковые строки дублями. Файлы с объединёнными заголовками, паролями и макросами предварительно приведите к плоской таблице. Предпросмотр не исполняет формулы.

В «Отчётах» доступны Excel с отдельными листами сводки / заказов / денежных операций и печать в PDF средствами браузера («Сохранить как PDF»). Финансовые выгрузки доступны владельцу, менеджеру и бухгалтеру; для мастера они закрыты.

## Резервные копии и восстановление

Docker-служба `backup` делает копию при старте, затем каждые 24 часа. Архивы находятся в `backups/` и содержат согласованный снимок PostgreSQL и неизменяемые версии файлов. Автоматическое удаление старых копий не включено. При остановленном Docker новые копии не создаются.

Ручная копия:

```bash
npm run backup
```

Без Docker, при доступных `pg_dump` и `pg_restore` версии 17 в PATH:

```bash
npm run backup -- --native
```

При необходимости задайте полный путь к утилитам через `PG_DUMP_BIN` и `PG_RESTORE_BIN`. Копии содержат персональные данные и хэши паролей; храните их с ограничением доступа и регулярно переносите на другое устройство. `.env` в архив не включается; храните защищённую копию конфигурации отдельно.

Восстановление выполняется в **отдельную пустую базу** и отдельный каталог документов. Рабочая база не перезаписывается. Это также позволяет безопасно проверить копию.

Пример PowerShell после создания пустой базы `looma_recovery`:

```powershell
$env:RESTORE_DATABASE_URL='postgres://looma:ПАРОЛЬ@127.0.0.1:5432/looma_recovery'
$env:RESTORE_STORAGE_DIR='C:\LOOMA\storage-recovery'
npm run restore -- 'C:\LOOMA\looma-crm\backups\looma-ВАША-ДАТА.tar.gz'
```

Для обычного PostgreSQL добавьте `--native`. При Docker целевая база должна находиться в сервисе `db` того же Compose-проекта. После восстановления остановите приложение и временно задайте DATABASE_URL / STORAGE_DIR на восстановленные данные для проверки. Docker-конфигурация использует POSTGRES_DB и bind mount: переключите POSTGRES_DB и путь `./storage` только после проверки. Старую рабочую базу и файлы сохраните до окончания проверки.

Проверяйте вход, список заказов, суммы, историю и скачивание нескольких версий документов не реже раза в месяц. При восстановлении на общем сервере отзовите старые сессии: `DELETE FROM sessions;`.

## Собственный домен в будущем

Покупать домен для локального запуска не требуется. Для доступа сотрудников через интернет перенесите приложение, PostgreSQL и документы на выбранный сервер. Затем настройте DNS A-запись, HTTPS-прокси (пример `docs/Caddyfile.example`), задайте APP_ORIGIN на точный `https://crm.ВАШ-ДОМЕН`, COOKIE_SECURE=true и TRUST_PROXY=true. Пример override — `docs/compose.domain.example.yaml`. Порт PostgreSQL не открывайте наружу. Приложение за Caddy оставьте на 127.0.0.1:3001.

Для работы в локальной сети нужно отдельно настроить адрес привязки, Windows Firewall и APP_ORIGIN. `localhost` доступен только с того компьютера, где запущен сервер; покупка домена сама по себе не делает локальную базу доступной коллегам.

## Проверки и структура

```bash
npm run check
npm run build
npm audit --omit=dev --audit-level=high
```

Для API-тестов создайте **отдельную тестовую базу** с `test` в названии. Тесты очищают её.

```powershell
$env:TEST_DATABASE_URL='postgres://looma:ПАРОЛЬ@127.0.0.1:5432/looma_test'
npm test
```

`server/routes` — REST API по разделам, `server/security.ts` — права и проекции данных, `db` — последовательные SQL-миграции, `shared` — типы и функции денег, `web/src` — React-интерфейс, `scripts` — запуск / копии / GitHub, `tests` — расчёты и сквозные сценарии API.

Результаты выполненной проверки и ограничения среды — в `docs/ACCEPTANCE.md`. Перед переносом реальных данных выполните проверку на своём PostgreSQL и копии обезличенного реестра компании. Нагрузочная проверка на 10 000 заказов / 100 000 операций и тест полного развёртывания Docker на Windows пока не выполнены.
